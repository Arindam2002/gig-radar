# Post to archive: write and publish a blog post

The archive site lives in its own repo at `<ARCHIVE_DIR>` (a Quartz v5
site). Posts are plain markdown in `content/blog/`. A push to `main` deploys
the site to `<SITE_URL>` within a minute or two. The study section next to
the blog is generated by gig-radar's publish export; this skill never touches
it.

Verbs: `/post-to-archive new "Title" [--from <topic-slug>]`,
`/post-to-archive preview`, `/post-to-archive publish <post-slug>`,
`/post-to-archive list`.

## new "Title" [--from <topic-slug>]

1. Slug the title: lowercase, hyphens, no punctuation. The file is
   `content/blog/<slug>.md`. Refuse if it exists.
2. Write the file with this frontmatter and nothing else in it yet:

   ```
   ---
   title: "<Title>"
   date: <today, YYYY-MM-DD>
   tags: []
   draft: true
   ---
   ```

3. If `--from <topic-slug>` is given, generate that topic's writing pack from
   the gig-radar checkout and put it NEXT to the post, not in it:

   ```
   cd <PROJECT_DIR> && python -m jobscout.pack <topic-slug>
   cp <PROJECT_DIR>/study/packs/<topic-slug>.md <ARCHIVE_DIR>/content/blog/<slug>.pack.md
   ```

   Then prepend `---\ndraft: true\n---\n` to the copied pack so it never
   builds. The pack holds the topic body, its flashcards, the diagram path,
   and the user's own highlights and notes: raw material to write from, not
   text to paste. Say where it is and that `publish` deletes it.
4. Tell the user the path and stop. The user writes the post themselves;
   do not draft prose for them unless they ask.

## preview

```
cd <ARCHIVE_DIR> && npm ci && npx quartz plugin restore && npx quartz build --serve
```

(`npm ci` and `plugin restore` are only needed the first time or after a
`git pull`.) Report the local URL (`http://localhost:8080/`). Drafts are
excluded from the build, so to preview a draft, temporarily build with the
flag flipped and flip it back, or tell the user to set `draft: false`
locally without committing.

## publish <post-slug>

Before anything else, read the post in full and check:

- Frontmatter has `title`, `date` and `tags`.
- Nothing names the user's employer, a company from their job pipeline, or
  identifying details of their production systems; nothing quotes a resume
  drill (`Interviewer probes`, `The claim`, `[FILL:`). If you find any, stop
  and show the lines; do not publish.
- Wikilinks like `[[some-topic]]` point at a page that exists under
  `content/study/` or `content/blog/`; warn about any that do not (they
  would render as broken links).
- Style nits worth a warning, never a block: em dashes, emoji, a missing
  first paragraph.

Then:

1. Set `draft: false` in the post's frontmatter. Delete
   `content/blog/<post-slug>.pack.md` if it exists.
2. Commit with a plain message, `Post: <Title>`, and push `main`. Never add a
   `Co-Authored-By` trailer or any assistant attribution to the commit.
3. Wait for the deploy workflow (`gh run list --repo <OWNER>/<ARCHIVE_REPO>
   --limit 1` until it completes) and report the live URL:
   `<SITE_URL>/blog/<post-slug>`.

## list

Print every file in `content/blog/` with its title, date, draft flag, and the
live URL for published ones.

## Rules

- Posts are the user's writing. Fix typos only when asked; never rewrite
  voice.
- The `.pack.md` files are private working material: never commit one with
  `draft` missing, never publish one.
- Never edit `content/study/`; the export owns it.
